## Implementation Goal

Improve encounter fidelity without disrupting:

* Existing provider diagnosis bundles
* Existing final-rule behavior
* Current users
* Existing saved encounters
* Non-hormone SOAP generation
* Existing API response formats consumed by the frontend
* Current note personalization behavior

Do not remove or weaken the provider-configured perimenopause diagnosis bundle. The bundle should remain authoritative for diagnosis classification and assessment organization.

The changes must improve what is extracted, preserve the provider’s interpretation, and verify the final note against the encounter.

## Implementation Order

Please implement the following in stages, with backward-compatible defaults.

### Phase 1: Expand the Stage 1 extraction schema

Do not continue using a flat array with textual prefixes as the primary data structure.

Instead of requiring strings such as:

`[START] testosterone 7.5 mg weekly`

create structured objects.

Add a field similar to:

```ts
treatment_actions: Array<{
  action:
    | "start"
    | "continue"
    | "increase"
    | "decrease"
    | "stop"
    | "hold"
    | "trial"
    | "consider"
    | "defer"
    | "declined";
  item_name: string;
  item_type:
    | "prescription"
    | "supplement"
    | "otc"
    | "device"
    | "lifestyle"
    | "other";
  previous_dose?: string | null;
  new_dose?: string | null;
  route?: string | null;
  frequency?: string | null;
  status:
    | "confirmed"
    | "conditional"
    | "future_consideration"
    | "discussed_only";
  reason?: string | null;
  timing?: string | null;
  evidence_quote?: string | null;
}>;
```

The exact TypeScript structure may be adjusted to fit the current architecture, but the information must remain structurally distinct.

Do not rely only on action prefixes embedded in strings. Those are difficult to validate and easy for downstream prompts to misinterpret.

Keep the existing `medication_changes_discussed` field temporarily if other parts of the application depend on it, but populate the new structured field and migrate downstream generation to use the structured field. Do not break existing consumers.

### Phase 5: Update the Stage 4 note-generation prompt

Change the bundle instruction so that it clearly separates diagnostic organization from individualized reasoning.

Use language with this intent:

> The matched provider diagnosis bundle determines the preferred diagnostic classification and Assessment heading. It does not replace the patient-specific assessment narrative. Under the bundle heading, summarize the symptoms, patterns, relevant laboratory context, prior medication response, adverse effects, provider interpretation, treatment rationale, shared decision-making, and staged plan that are specific to this encounter.

The generator should consume the structured fields directly and follow this priority:

1. Explicit provider decisions
2. Confirmed starts, stops, and dose changes
3. Provider interpretations
4. Safety screening
5. Treatment rationale
6. Staged and conditional plans
7. Patient-specific symptom and laboratory context
8. Provider diagnosis bundles
9. General medical knowledge

General model knowledge must not override an explicit provider interpretation or convert a discussed option into a confirmed plan.

### Phase 6: Replace the unconditional GLP-1 weight-diagnosis rule

Remove the current rule that automatically requires an E66.x, overweight, or metabolic diagnosis whenever a GLP-1 or weight discussion appears.

Instead, reconcile weight diagnoses using available evidence:

* Use current BMI when documented.
* Use an explicit provider diagnosis when stated.
* Use existing active chart diagnoses when appropriate.
* Distinguish current obesity from history of obesity, overweight, weight maintenance, insulin resistance, and medication management.
* Do not infer obesity solely from GLP-1 use.
* Do not convert a weight-management discussion into a new diagnosis without supporting evidence.

Suggested logic:

```ts
if (providerExplicitlyDiagnosedWeightCondition) {
  useProviderDiagnosis();
} else if (currentBmi != null && currentBmi >= 30) {
  allowObesityDiagnosisIfClinicallySupported();
} else if (currentBmi != null && currentBmi >= 25) {
  allowOverweightDiagnosisIfClinicallySupported();
} else if (historyOfObesityOrWeightLossTreatmentIsDocumented) {
  useHistoryOfObesityOrWeightManagementLanguage();
} else {
  doNotForceWeightDiagnosis();
}
```

Do not hard-code a diagnosis based on one data point when provider settings or chart history may provide more complete context.

Also ensure that the diagnosis title and ICD-10 code agree. For example, do not display “Obesity” with E66.3.

### Phase 7: Strengthen QA using both extraction and transcript evidence

The QA stage should continue comparing the note to structured extraction, but add a targeted raw-transcript audit for high-risk omissions.

The targeted categories should include:

* Prescription starts and stops
* Dose increases and decreases
* Supplement starts and stops
* Abnormal laboratory management
* Deferred versus initiated therapies
* Follow-up timing
* Medication safety screening
* Provider interpretations
* Staged treatment plans
* Adverse effects that affected route or dose selection

Do not ask the QA model to reinterpret the entire encounter from scratch. Give it a focused task:

> Identify explicit provider actions or interpretations in the transcript that are absent from or contradicted by the generated note.

The QA result should return structured discrepancies such as:

```ts
{
  category: "missing_treatment_action",
  severity: "high",
  transcript_fact: "Increase progesterone from 50 mg to 100 mg nightly",
  note_conflict: "Note states only to continue progesterone 50 mg",
  recommended_correction: "Update medication list and plan"
}
```

Then apply only evidence-supported corrections.

### Phase 8: Address transcript length safely

Do not silently truncate the last portion of a long transcript for QA.

Please inspect actual model context limits and implement one of the following:

* Use the full transcript when safely within the model limit.
* Use chunked, overlapping extraction for very long transcripts.
* Create a targeted action/decision extraction from all chunks and provide that complete structured result to QA.
* Explicitly record when any content had to be excluded.

The later portion of an encounter often contains the final medication decisions and follow-up plan, so truncating the end creates a particularly high clinical risk.

### Phase 9: Add deterministic validation before the final note is returned

Add code-based checks where possible rather than leaving every check to another language-model call.

At minimum, validate:

1. Every confirmed `start`, `stop`, `increase`, or `decrease` action appears in the final plan.
2. Every `future_consideration` is phrased as conditional and not as initiated.
3. Medication dose changes do not conflict with the active plan.
4. Diagnosis labels and ICD-10 codes are consistent.
5. BMI and weight diagnoses do not directly conflict.
6. Follow-up timing is internally consistent.
7. An explicitly deferred treatment is not listed as started.
8. An explicitly stopped supplement is not listed under “continue.”
9. A provider interpretation is not reversed in the final note.
10. No diagnosis is introduced solely because a medication is commonly used for that diagnosis.

When a deterministic validation fails, send only the relevant discrepancy back through a focused repair step rather than regenerating the entire note unnecessarily.
