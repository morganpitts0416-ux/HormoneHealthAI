Interpretation

If I speak and the RMS/peak meter is essentially flat:

The defect is before MediaRecorder. We then investigate microphone selection, browser permissions/device state, muted/ended track behavior, or competing capture ownership.

If the meter clearly responds to my voice but the resulting WebM is still approximately 470 bytes/sec and STT returns nonsense:

The microphone track is good and the failure is in MediaRecorder/browser encoding or Blob production. At that point, stop investigating microphone selection.

If track state changes during recording — for example muted=true, readyState=ended, stream.active=false, or device/settings unexpectedly change — capture the transition in the diagnostic UI so we can correlate it with the failure.

Add focused tests for diagnostic initialization/cleanup and use of the same stream, run the production build, and do not deploy automatically.
